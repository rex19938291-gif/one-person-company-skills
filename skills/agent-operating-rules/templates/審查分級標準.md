# 審查分級標準

適用：所有交給審查者的程式審查與複審。目的：只擋「正常使用下會真的發生、而且有實際後果」的問題，避免一輪接一輪燒額度。功能正常、風險可控就可以通過，不追求一百分。

用法：主對話派審查時，把下面「貼進派工詞」整段原文放在派工詞最前面；複審也要貼。主對話自己的判定規則在 `rules/core-rules.md`「審查分級」。

---

## 貼進派工詞（原文照貼）

【審查分級標準，必須遵守】
1. 你只負責找「會讓功能在正常使用下出錯，或造成實際損害」的問題。功能正常、風險可控就判 PASS，不需要完美。
2. 每一項 P0／P1 都必須寫出三件事，缺任何一件就只能列 P2：
   - 發生條件：在這個系統的實際使用方式下，具體怎麼觸發（不是理論上可能）。
   - 發生機率：正常使用下多久會碰到一次的估計（例如每天、每週、幾乎不會）。
   - 影響：你看到什麼、損失什麼、能不能自己恢復。
3. 分級：
   - P0：資料毀損或遺失、金流或帳務錯誤、資安或個資外洩、正式服務整個不能用。只要有合理發生路徑就擋。
   - P1：正常使用下「每週會碰到一次以上」的功能錯誤，或錯誤數字會被你當真且無法察覺、不會自己恢復。擋上線。
   - P2：其他所有問題，包括需要特殊時序或多個罕見條件同時成立的競態、極端資料量、刻意人工操作才會觸發、會自己恢復或畫面有提示的狀況、說明文字或測試覆蓋不足。列待辦，不擋上線。
4. 只推導出來、沒有在這個系統的實際設定下確認會發生的情境，一律列 P2，並註明「推導未證實」。
5. 複審只看「上一輪 P0／P1 是否解決」與「這次修改本身有沒有新的 P0／P1」。已通過的部分不重審，不另外擴大範圍找新問題。
6. P2 最多列 5 項，挑最值得做的；其餘省略。
7. 結論第一行只能是 PASS 或 FAIL。只要沒有 P0／P1 就是 PASS（可附 P2 待辦）。
