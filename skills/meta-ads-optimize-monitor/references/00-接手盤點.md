# 00 接手盤點（每個新專案必做，全程唯讀）

## A. 先讀本專案自己的紀錄

依序找，找到就讀最新段，舊段用關鍵字取：

1. 專案交接檔（現況、已定案決策、待決事項、禁止事項）。
2. 專案的廣告策略文件、提案、漏斗規劃表、素材規格庫與台帳。
3. 決策者過去的裁示：粉專與 IG 身分、到達頁、受眾分層、預算與目標、哪些動作要逐次核准。
4. 已經在跑的排程或常駐程式（每日對帳、成效報告、預算核准卡、停損程式）。**新排程不得和它們搶同一件事**（trigger-ownership）：同一個動作只能有一個負責者。
5. 跨專案教訓檔（用專案名、平台名、症狀搜尋）。

讀完寫一段「本專案策略摘要」，每一點附來源檔與日期。來源互相矛盾時以最新裁示為準，並在規劃單列出矛盾。

## B. 唯讀盤點廣告帳號

用平台官方連接器或自建 API 工具，只用讀取：

- 帳號：幣別、時區、狀態、花費上限、可用的連線方式（有些帳號不開放官方連接器）。
- 投放中的行銷活動與廣告組合：名稱、預算層級（活動預算或組合預算）、每日預算、最佳化目標與轉換事件。
- 每則投放中廣告用的是哪個粉專與 IG 身分（看素材的 object_story_id 前綴或 actor）。
- 近 7 天、近 3 天、今天：花費、曝光、連結點擊、到達頁瀏覽、結果數（找出這個專案真正的結果 action_type，自訂事件常是 `offsite_conversion.fb_pixel_custom` 或 `offsite_conversion.custom.<編號>`）、購買。
- 逐日 14 天的花費與結果，看趨勢與波動。
- 審查狀態：被拒、審查中、申訴中的廣告。
- 自訂受眾的大小（互動型受眾常卡在「太小無法使用」）。

## C. 對照找落差

把「策略說要做」與「帳號實際狀態」並排，例如：

| 策略裁示 | 帳號現況 | 落差 |
|---|---|---|
| 改用新粉專投放 | 投放中廣告全在舊粉專 | 新粉專尚未上線 |
| 互動受眾立刻建 | 查不到該受眾 | 未建或已刪，待確認 |

落差只列出、建議做法，不自行補做。

## D. 判斷適用模式

| 模式 | 適用 | 排程可自動做 |
|---|---|---|
| 完整自動優化 | 有明確目標筆數、總預算、每筆成本上限，決策者授權自動調整 | 盤中加預算、每日結算加減、素材開關、缺集重建、額滿下架 |
| 只加不減／只減不加 | 決策者只放行單一方向 | 只做放行的方向 |
| 只監控與建議 | 沒有目標或預算紀錄、帳號規定預算改動要逐次核准、客戶正式帳號 | 讀數、記錄、異常通知、產出建議；動作走既有核准流程 |

沒有目標與預算的專案，用「效率基準」代替目標：以近 14 天的每筆成本中位數當基準，偏離基準 ±30% 才提醒。這只是監控用的參考線，不是決策者定的目標，回報要寫明。
