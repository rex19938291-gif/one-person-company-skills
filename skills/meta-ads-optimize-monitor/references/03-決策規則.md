# 03 決策規則

## 零、結果數怎麼讀（所有規則的前提）

- **只認專案設定檔指定的 action_type，完全相等比對**。名單類常見是 `offsite_conversion.fb_pixel_lead`（沒有才用 `lead`）；自訂事件可能是 `offsite_conversion.fb_pixel_custom`。名稱「含有」lead 的其他項目一律不算，例如 `offsite_content_view_add_meta_leads` 其實是瀏覽內容——曾因用「包含 lead」比對，把 0 筆名單讀成 7 筆而誤加預算。
- **以網站實收為準，對不上不問人**：平台數字與網站不一致時，自己依序查名單試算表、名額／場次統計、網站表單筆數（只數筆數，不讀個資），以網站表單為最終依據；只有網站資料讀不到時才通報。
- **任何加預算前，先用網站實收交叉核對**今天的結果數與每筆成本；網站實收低於平台數字時，以網站為準重新判斷。

以下是規則的「形狀」。每條的數字、是否自動執行，都以專案設定檔與決策者確認為準。以 C 代表每筆成本上限。

## 一、盤中成效好加預算（操作排程每輪檢查）

目的：成效好的組合不要因為預算中午花完而斷掉。
只在白天時段動作（例如 08:00–21:59；晚上剩餘時間短，不加）。要**同時**符合：

- 今天花費 ≥ 目前每日預算的 85%；
- 今天結果 ≥3 筆，且今天每筆 ≤ 0.8C；
- 持續有進單：最近 3 小時有新結果（hourly 分段，或與上一輪紀錄比較）；
- 距該組合上次盤中加預算 ≥2 小時，且今天盤中加預算 <2 次。

加法：每日預算 ×1.2 四捨五入（**每次漲幅 ≤20%**）。上限任一條會超過就不加或只加到上限：單一組合防呆上限、總花費硬上限、名額全滿、決策者另訂的合計上限。
每次加都記錄原值→新值、今天花費／結果／每筆、最近進單時間，並在輸出第一行提醒主對話。

## 一之二、盤中煞車（v5.6 放寬：有結果就等晚上看全天）

目的：成效差的組合不要整個下午繼續燒錢。但半天、結果少的時候，每筆成本雜訊很大（下午 1 筆時每筆看起來很貴，晚上多進 2 筆就回到正常），太早降會砍到好的組合、又重置學習期。所以分兩段判斷，以**網站實收**為準：

- **白天**（`brake_window`，例如 12:00–21:59）：只有「今天花費 ≥ `brake_zero_spend_multiple`×C（預設 2C）且網站實收 0 筆」才降。
- **今天網站實收 ≥1 筆**：白天不降；到 `brake_evening_check`（預設 21:00）那一輪看全天：今天花費 ÷ 網站實收 > `brake_cost_multiple`×C（預設 1.6C）才降。
- 動作：該組合每日預算降 `lower_pct`（預設 20%），下限 `brake_floor_budget`；已在下限就不再降、只回報。每組每天最多一次；當天盤中加過的，先撤回到加之前的數字算這一次。
- 本條**取代** v5.5 以前的「今天花費 ≥ 每日預算 50% 且每筆 > 煞車門檻」（`brake_spend_ratio`、`brake_cost_threshold` 停用）。
- 隔天由每日結算「降後退回」判斷（見二、第 3-2 項）。

## 一之三、盤中碰上限加碼（成效好卻被當日預算卡住）

目的：不要再發生「成效好，下午就把當日預算花完，晚上的好時段斷掉」。設定檔 `cap_raise_enabled=true` 才做。

- 在 `cap_raise_window`（預設 12:00–20:59），主組合同時符合：今天花費 ≥ 每日預算 × `cap_raise_spend_ratio`（預設 0.9）；今天網站實收 ≥ `cap_raise_min_results`（預設 2）；今天每筆 ≤ `cap_raise_cost_ratio`×C（預設 0.65C）→ 每日預算 +20%（四捨五入），一天最多一次。
- 限制：不超過 `unit_budget_ceiling`；過預算守門（有結束日的專案見二之二）；當天已盤中降過就不加。
- 與「一、盤中成效好加預算」的關係：一是條件較嚴、可加 2 次的版本；一之三專治「下午就花完」。兩條都開時，同一天合計仍受 `raise_max_per_day` 限制，不重複加。
- 每次加碼在調整紀錄寫「盤中加碼」與原值→新值、今天花費、網站實收、每筆，並在輸出第一行提醒主對話。

## 二、每日結算（每天固定時間後第一輪做一次；需要取捨，交判斷力較強的模型）

**漏跑補做**：結算排在 `settle_time`（例如 09:00）後的第一輪；同一天到 `settle_catchup_until`（預設 12:00）前，任何一輪發現調整紀錄沒有今天的結算列，就立刻補做並在紀錄寫「補做」。過了補做時限仍沒做 → 寫進待決策佇列，不要等主對話自己發現。

**加減碼看合計，不看單日**：第 4、5 項的「近 3 日」都是最近 `settle_window_days`（預設 3）個完整日（不含今天）的**合計花費 ÷ 合計網站實收**，不是每天每筆的平均；加碼與降碼都不用「前一天」或「連 2 天」單日判斷——單日名單少時每筆雜訊很大，用單日會來回加減。（第 3、3-2 項是針對昨天盤中動作的回收，仍看昨天整天。）

依序判斷，每個組合各自判斷，每個動作寫數字與原因：

1. 累計花費 ≥ 硬上限 → 暫停，通知決策者。
2. 連續 5 個完整日每筆 > 1.6C（或花費 ≥4C 仍 0 筆）→ 暫停，請決策者決定，不自行再開。
3. 昨天有盤中加預算：昨天整天每筆 ≤ C → 維持；> C → 降 20%，一天一次，直到回到加之前的數字。
3-2. **降後退回**：昨天被盤中降過的組合，昨天整天網站每筆 ≤ C → 一次退回降之前的預算（回到原值，不受 20% 限制，因為不是新加碼）；> C → 維持。退回的當天不再另外 +20%；本項優先於第 4、5 項。昨天先盤中加、後盤中降（煞車先撤回加碼）的組合只看本項，退回值為昨天開始時的預算。
4. 近 3 日合計 ≥6 筆且合計每筆 ≤ `settle_raise_cost_ratio`×C（預設 0.8C；採預算前移的專案常設 1.0）→ 每日預算 +20%（距上次結算加預算滿 `settle_raise_min_days` 天，預算前移專案可設 1；受防呆上限與預算守門限制）。
5. 近 3 日合計每筆 > `settle_lower_cost_ratio`×C（預設 1.3C，採預算前移的專案常設 1.0；且花費夠多）→ 採預算前移的專案：直接降 20%（設下限），不必先等素材處理；其他專案：先照 references/11 拆一次漏斗分段，確認貴在哪一段（到站率低先查轉址與速度）；再 **先處理素材**：投放中的廣告最多暫停 2 則（先關「花費 ≥1.2C 仍 0 筆」，其次每筆最高）；每集或每主題至少留 1 則、整體至少留 4 則。沒有可關的素材、且距上次關素材滿 3 天仍偏高 → 才降預算 20%（設下限）。
6. 合計上限只在「昨天合併每筆 > C」時套用，超過先降最大的組合，每次 ≤20%、一天一次。
7. 素材開回：被暫停的廣告，若其他投放中廣告每筆連續 2 天高於它，或已暫停滿 3 天，一次只開回 1 則（不改內容），讀回確認。
8. 其他 → 維持不動，寫原因。沒有動作也記一列「維持不動」與判斷數字。

## 二之二、預算前移＋保留款守門（有結束日、總預算固定的專案；`front_load.enabled=true` 才做）

目的：成效好就把後段的預算挪到前面用，提早達標、早點脫離學習期；同時保留一筆款項給後段，總花費永遠不超過硬上限。

- 主組合上限改用 `front_load.unit_ceiling`；加碼節奏不變（每次 ≤20%，結算與盤中各自的次數限制照舊）。
- **保留款守門**：每次加碼前算「累計已花 ＋ 投放中各組合（加碼後）每日預算合計 × 到 `front_load.reserve_from_date` 前的剩餘天數（含今天）」，必須 ≤ `goals.hard_cap` − `front_load.reserve_amount`。超過就只加到剛好不超過的整數，或不加。
- **保留日起**：投放中每日預算合計調到 ≤（硬上限 − 累計已花）÷ 到結束日剩餘天數（向下取整），每天最多降 20%，調到為止。
- **名額快滿就停加碼**：某場已達名額且其他場都 ≥ 名額 × `front_load.stop_raise_other_ratio`（例如 0.8）→ 停止加碼，回報決策者決定。
- 每次加減在調整紀錄寫：原→新、前一日與近 3 日合計的花費／網站實收／每筆、累計已花、保留日前預估、保留款剩餘。
- **保留款比例的提醒**：保留款要按「最後收單日之前還沒開的場次，還差多少人」來估，不要只抓一個固定金額。早報名的人離上課越遠、出席率越低，所以後面場次的預算要留夠，讓這些人能在接近上課時才報名。估法範例：後面場次還差人數 × C × 0.4–0.5。

## 二之三、每日回報的結果數要分兩種寫

報名表有「其他場次（有新場次時通知我）」「候補」這類不屬於任何一場的選項時：

- 它算一筆網站報名，**計入每筆成本與所有預算加減判斷**（預算照總數算）。
- 它不是場次：不算任何一場名額、不參與額滿下架與「還有名額的場次」判斷，排程不得把它從表單拿掉。
- 每日結算與每日回報另列「選了實際場次的報名數」與其每筆成本（排除這類選項），和含它的總數並列；場次人數表另列一行，跟各場分開寫。

## 二之四、進度落後時放寬成本上限（`pace_relax.enabled=true` 才做）

只守成本會一直降預算，結果人數達不到；只追人數又會超支。用「進度」當開關，兩邊都顧到。

每次結算先算：

- 還差人數＝總目標 −（已報名合計，**不含**「其他場次／候補」這類不算名額的選項，見二之三）。
- 每日需要＝還差人數 ÷ 到最後收單日的剩餘天數（含今天）。

判斷：

- 最近 `pace_relax.window_days`（預設 3）個完整日的**每日實收平均 < 每日需要** → 當天所有加碼、減碼、退回的判斷，成本上限 C 一律改用 C_slack（`slack_multiplier`×C，預設 1.2C）。
- 進度跟上了（平均 ≥ 每日需要）→ 回到原本的 C。
- 總預算與保留款守門（二之二）照舊，不受這條影響。
- 「人數目標」以設定檔 `target_basis` 為準（報名數或出席數），算還差人數與每日需要時口徑要一致。
- 取代關係：本節只在落後時把第 1–8 項與盤中規則裡的 C 換成 C_slack，不新增動作；進度與成本上限衝突時哪個優先，要先請決策者定好（見 SKILL.md「開工前確認清單」）。

回報時固定寫四個數字：**還差、每日需要、近 3 日平均、今天用的 C**（用 C 或 C_slack）。

## 三、素材：缺集才重建、成效差才換文案

- **缺集才重建**：同一集或同一主題沒有任何投放中、審查中的版本，最新版本被拒，才重建；該集已有通過的版本，其他版本被拒一律不重建、不申訴。每集每天重建次數設上限。
- **換字規則**：只換最可能觸發審查的詞，換成同樣具體、意思相同的說法；分層換（第 1 層換最重的詞 → 第 2 層 → 第 3 層 → 第 4 層換圖），用完仍被拒就停，請決策者決定。
- **賣點不可模糊**：數字、案例、職業、價差口徑、核心承諾不得刪改或變含糊。換完自己讀一遍，覺得賣點變模糊就不建，記錄並請決策者決定。換字稿建立前交另一個唯讀審查者逐條比對。
- **成效差才換新文案**：單則廣告累計花費 ≥ C、曝光 ≥300、結果 0 → 為該集上新版本（每則廣告只觸發一次、每集每天最多 2 次）；該集已有另一則表現好的就不換。
- **舊版退場**：新版通過且開始正常投放（曝光 ≥200 或花費 ≥ 一小段）後，暫停同集較早的舊版；舊版本身表現好就保留。
- **申訴過仍被拒超過 48 小時**：暫停（不刪除）。
- **素材文案與案例**：成果類說法用「有機會」語氣；案例數字只寫真實發生過的，並在圖片角落與文案結尾加「真實案例，結果因人而異」這類警語；不同比較基準的數字（例如對鑑價的折數與對原價的折數）不要放在同一則；案例圖用真實學員照片（臉部遮蔽、可辨識資訊模糊），不要拿講師或代言人照片代替學員。
- 命名帶集數與版本（例如「EP03｜轉換-v2換字版」），版面一句一行、段落不超過 4 行。

## 三之二、新素材測試組合（主組合被單一勝出素材吃掉預算時）

- 症狀：同一組合裡一則廣告吃掉大部分花費，新上的素材通過審查很久仍分不到曝光。
- 做法：複製主組合的受眾與最佳化設定，開一個「新素材測試組合」，每日固定小額（例如主組合的三到四成，從主組合移過來，總預算不變），**測試組合不做盤中加減**。新素材放進測試組合，主組合裡對應的舊版暫停。
- 評估：上線滿 3 個完整日後，每日結算時看測試組合：某則結果數 ≥2 且每筆 ≤C（依網站實收交叉核對）→ 判為勝出，用同一份素材（同 creative）建回主組合並暫停它要取代的舊版；花費 ≥1.2C 仍 0 筆 → 在測試組合暫停。
- 收尾：測試組合剩不到 2 則有效廣告時暫停它，把預算分次加回主組合（每次 ≤20%）。
- 每次判定都記錄，並在輸出第一行提醒主對話。

## 四、名額與場次

- 平常只讀「場次人數」資料（已扣測試）；某場第一次到 80% 名額 → 通知；≥ 名額 → 回網站確認實際筆數 ≥ 名額才下架。
- 下架：先備份表單欄位原文 → 只移除該場選項 → 讀回選項數少 1、其他不變 → 清到達頁快取 → 抓到達頁原始碼確認該場文字已消失、其他場仍在 → 記錄並通知。剩 0 個選項時不移除，改走全部額滿。
- 全部額滿或已過期 → 暫停轉換活動並通知；表單選項不清空。
- 不重新上架、不刪報名資料、不改頁面文案；同一事件只記一次。

## 四之二、主動洞察檢查（整點那一輪做，資料用平台唯讀＋網站實收）

| 檢查 | 觸發條件（數字可調） | 自己處理 | 回報決策者 |
|---|---|---|---|
| 投放集中 | 同組合一則吃掉 ≥80% 花費，且有通過審查滿 24 小時的新素材曝光 <50 | 把被壓住的素材移到測試組合 | 測試組合已有同素材時 |
| 新素材被拒 | 讀審查回饋；讀不到就比對同批通過素材的差異字句 | 第一次：照換字規則改寫一次、由排程自己建立 | 同一則第二次被拒 |
| 勝出素材疲乏 | 近 7 天結果最多的那則，今天每筆 > 它近 3 日平均 2 倍且頻率 >2.5，或連 2 天每筆 > 1.6C | — | 一律回報，不自行暫停勝出素材 |
| 點擊變貴 | 今天每次點擊成本 > 近 7 天平均 1.5 倍（今天點擊 ≥15） | — | 附各組合每千次曝光成本，指出哪一組造成 |
| 報名頁轉換掉 | 今天網站廣告訪客 ≥20，網站實收 ÷ 網站廣告訪客 < 近 7 天平均一半（網站基準，見 references/11；網站訪客讀不到時才用平台到頁並標「平台口徑」，同一比較兩邊口徑要一致） | 先自查報名頁（回應正常、表單欄位與送出按鈕在、資料有進來） | 頁面或表單壞了；或頁面正常但轉換下降（附各素材網站訪客與報名，依 utm_content 拆） |
| **追蹤落差（最高優先）** | 平台結果與網站實收差 ≥3 筆，或任一段平台事件比網站少超過 `funnel.source_mismatch_ratio` | 依「結果數怎麼讀」自己核對；確認是平台少收到時，列為第一優先修正項（修法見 references/11「追蹤完整度」），排在所有其他洞察之前 | 一律回報，放在回報第一行；修追蹤需要改網站設定時用選項卡片請決策者決定 |

判斷界線：本專案規則已寫明的動作（移到測試組合、改寫重建一次、暫停 0 結果素材、規則內加減預算）自己做並記錄；新建組合、超出規則的預算調整、暫停勝出素材、改報名頁、規則沒寫到的情況，一律在輸出第一行寫「需要主對話決定：<問題>｜建議：<做法>｜理由：<數字>」，不要自己做。

## 五、共通

- 每個動作都讀回確認；工具失敗等 30 秒重試一次，第二次失敗就停止該步並如實記錄。
- 規則沒寫到、需要取捨 → 不猜，記錄並在輸出第一行寫「需要主對話注意」。
- **規則互相衝突時不取捨**：同一輪兩條規則結論相反（例如一條要加、一條要降，或一條說「白天不調」、另一條說「碰上限就加」），排程不做任何一邊，寫進待決策佇列（附兩條規則原文與數字），輸出第一行提醒。
- **避免寫出衝突的規則**：排程指令檔新增或修改規則時，一律在標題或第一句寫明「取代前文哪一條」或「優先於前文所有衝突寫法」，同時把被取代的舊句改成「（已作廢，見 <新段名>）」，不要只在檔尾疊加新段；數字改動（上限、門檻）只留一個現行值。改完自己從頭讀一次，確認同一件事只剩一種說法。
- 停損程式等其他自動程式的動作只讀、只記錄，不去改它。
