# 04 排程分工與範本

## 分工原則

- **所有會改動廣告的事只放在一支「操作排程」**（每 10 分鐘）。另一支「每日回報排程」只讀、只記錄、只回報，不動任何廣告。兩支同時能改廣告就會互相打架。
- 和既有排程不重疊：專案已有每日對帳、成效報告、預算核准卡等程式時，新排程只補缺的部分，並在交接檔寫清楚誰負責什麼。
- 每支排程都有結束日；到期時自己停用並寫一列「排程已結束」。
- 排程不得再自建排程、背景常駐程式或自動喚醒。
- 無人值守時不開任何核准提示；需要決策者的事寫進輸出第一行與交接檔。

## 決策詢問與寫入分工

- 需要決策者決定的事，一律用原生選項卡片按鈕（例如 Claude Code 的 AskUserQuestion）問，建議選項放第一個並標「（建議）」，不要只寫在文字裡。
- 子代理只寫文案、設定與判斷建議；**寫入外部服務（建廣告、改預算、改網站）一律由排程本身或主對話執行**——子代理自行寫入常被權限擋下，也比較難追蹤。

## 模型分級（寫在排程 SKILL.md 首部）

- 排程本體：`model: sonnet`（讀數、比門檻、記錄、照規則加預算）。
- 需要取捨或改寫的工作，用子代理派判斷力較強的模型（例如 opus）：每日結算、換字重建與新文案、下架異常、規則沒寫到的狀況。子代理回報後由本輪讀回確認再記錄。
- 改程式或網站設定：執行者寫、另一個獨立的審查者唯讀審查、正式環境實測通過才算完成。
- 單純搜尋與摘要可用最便宜的模型。

## 排程 SKILL.md 範本：操作排程

```markdown
---
name: <專案代號>-ads-ops-monitor
description: <專案中文名> 廣告唯一的操作排程：盤中加預算、每日結算、素材開關、缺集重建、額滿下架、儀表板更新
model: sonnet
---
你是<決策者>的廣告操作助理。結束日 <YYYY-MM-DD>。回報繁中白話，行銷活動用中文名稱。

## 第零步：經驗回流
- 讀專案設定檔 <設定檔路徑> 的 records.experience_log、project.skill_version_applied 與 project.skill_auto_apply（缺值視為 false）；本 skill 正本為 <meta-ads-optimize-monitor 資料夾>/SKILL.md，建排程時填入實際可讀的位置。
- 讀經驗表的待同步列；每輪有新經驗就追加「時間｜誰發現｜新經驗與證據｜建議寫進哪裡｜狀態：待同步」，相同經驗不重複追加。新經驗只記不改規則；新版規則是否自動套用，依下方「版本跟進檢查」與本檔第 4、5 點。
- 最後回報固定另加一行「新經驗：N 條待同步」（N 為表內待同步總列數，沒有寫 0）。

## 第一步：要不要做
- 取帳號時區現在時間；超過結束日 → 停用本排程、記錄、結束。
- 讀專案設定檔 <設定檔路徑>（格式見 references/10），帳號、組合、事件名稱、目標、門檻、通知方式一律以它為準；欄位為 null 的規則只監控不動作。本檔不寫任何專案專屬數字。

## 第二步：讀狀態（唯讀）
- 帳號 <帳號>；只看設定檔列出的行銷活動。讀今天花費、結果（action_type=<…>）、每日預算、各廣告 effective_status。

## 第三步：照規則動作（只做設定檔允許的）
- 先讀網站實收（表單筆數或統計分頁），與平台結果數交叉核對；結果只認設定檔的 action_type（完全相等）。對不上以網站為準，網站讀不到才在輸出第一行通報。
- 盤中加預算、盤中煞車、素材處理、缺集重建、額滿下架……（逐條貼上本專案確認過的規則與數字）
- 每天結算那輪（含漏跑補做）做「版本跟進檢查」：依本檔「經驗回流與版本跟進」第 4、5 點讀取正本與完整版本紀錄，按各段數字比較版本；project.skill_auto_apply 為 false 或缺值時，只記經驗表「待套用」，由主對話套用；只有決策者明確選擇全部自動套用並設為 true，才由排程執行者先備份、寫入規則檔尾「skill 自動套用區」、讀回後更新套用版本並記表。兩種模式都遵守第 4 點護欄；讀不到正本、缺套用版本或版本紀錄不完整時，記「版本跟進未完成」與缺少項目，不猜、不標已同步，原有授權規則照常執行。

## 第四步：記錄
- 「需要主對話決定」的事：輸出第一行寫明，**並在 <設定檔 records.decision_queue> 檔尾追加一行**（格式見 references/09），不依賴任何對話還開著。
- 有動作或狀態變化才追加一列到 <紀錄位置>；整點那一輪不論有無變化追加摘要。只追加，不覆寫。

## 第五步：儀表板
- 執行 `bash <儀表板資料夾>/export-and-deploy.sh --project <專案代號>`；非 0 只在輸出寫「儀表板未更新：<最後一行>」，不重試。

## 不可做
- 只能做本檔寫明的動作。不刪除、不申訴、不改受眾版位、不加總預算、不對外發訊（通知腳本除外）。
最後回報 3 行內，另加「新經驗：N 條待同步」；需要決策者的事放第一行。
```

## 排程 SKILL.md 範本：每日回報排程（只讀）

```markdown
---
name: <專案代號>-ads-daily-report
description: 每天 <時間> 整理昨日成效與操作排程做過的調整，只回報不動廣告
model: sonnet
---
## 第零步：經驗回流
- 先讀專案設定檔 <設定檔路徑> 與 records.experience_log 的待同步列；本輪有新經驗就照「時間｜誰發現｜新經驗與證據｜建議寫進哪裡｜狀態：待同步」追加，相同經驗不重複追加。
- 版本跟進由操作排程每日結算那輪檢查並記表；本排程只讀版本差異待同步列並提醒，不重複登記、不改規則或套用版本。完整比對方式見本 skill references/04「經驗回流與版本跟進」。
- 最後回報固定另加一行「新經驗：N 條待同步」（N 為表內待同步總列數，沒有寫 0）。

## 每日回報
- 只讀平台數字，不得對平台或網站寫入；只可追加本專案紀錄與經驗表。
- 補紀錄表的每日數字；讀操作排程昨天到今天結算做了什麼。
- 回報順序：要決定的事 → 昨日與累計對照目標 → 昨天的調整與原因 → 名額／場次 → 追蹤檢查 → 其他異常。
- 每逢設定檔 `funnel.weekly_day`（預設週一）：照 references/11 多產出漏斗分段診斷（組合層＋素材層分段表、「最值得優化的一段」一句判讀與第二、三順位、與上週比較），追加到 `funnel.log` 指定的紀錄檔；只讀不寫。
- 回報送主對話統整，不直接通知決策者（除非專案設定檔另有規定）。
```

## 建立後

- 排程權限設成自動模式（無人值守不能停在權限提示）；工具若無模式欄位，建立後提醒決策者到 app 確認。
- 手動觸發跑一輪，讀回：紀錄有新列、儀表板時間更新、沒有預期外的寫入。這一輪的證據寫進交接檔。

## 建排程三條硬規則（2026-10-28 線上課程型客戶站實測補記）
1. **權限模式要在「自動」模式的對話裡建，且當下沒有子代理或背景工作在跑**：否則排程會以預設模式存檔，無人值守時卡在允許提示。建好看工具回覆是否寫「saved in Auto mode」，沒有就停用、改名舊的，在符合條件的回合重建。
2. **工作資料夾與指令檔路徑要同一種寫法**：排程 cwd 若是捷徑路徑，指令裡讀檔也用同一個捷徑；兩個不同捷徑指到同資料夾仍可能被當成資料夾外而跳提示（線上課程型客戶站每日回報 10/27 卡住的原因之一是 cwd 設在別的專案）。
3. **每輪「一開始」先封存舊的同名排程對話，只留最新 3 則**（放在最後會因輪次提前收尾而被略過，A 客戶 10/28 實測累積 136＋8 則；排程改過名稱時新舊標題都要比對）（不要用全域「閒置 N 天封存」，會封到一般對話）：list_sessions 篩標題前綴、isRunning=false、非本輪，依 lastActivityAt 保留 3 則，其餘 archive_session，每輪最多 40 則，絕不 delete_session。
模型：每 10 分鐘操作排程用 Sonnet（照規則讀數與加減預算），需要取捨或改寫文案時在排程內派 Opus 子代理；每日回報用 Sonnet；每週檢討 Sonnet 主體＋Opus 寫建議。排程建好時 notifyOnCompletion 設 false，待決事項改寫待決策佇列。

## 經驗回流與版本跟進（v5.21）

排程每天會碰到新狀況：哪個字被拒、平台有什麼限制、規則讀錯造成空等、哪個做法有效。這些如果只留在當輪回報裡，下一輪、下一個專案還會再踩一次。所以固定走一條回流路：

1. **新經驗只記不改，版本套用另依第 4、5 點**：每輪有新結果、新規則或新做法，就在專案的「經驗沉澱待同步」表追加一列（時間｜誰發現｜新經驗與證據｜建議寫進哪裡｜狀態：待同步；位置讀設定檔 `records.experience_log`，預設 `docs/經驗沉澱待同步.md`），回報固定加一行「新經驗：N 條待同步」。只跟文案換字有關的，排程可以直接寫進專案自己的換字規則檔。
2. **主對話同輪同步三處**：看到新列，同輪寫進 ① 正在跑的排程規則（專案現行做法）② 本 skill（去掉專案名稱與編號的通用寫法，改版後推上公開倉庫）③ 跨專案教訓正本（會在別的專案重犯的坑）。寫完把該列改成「已同步」。
3. **主對話自己發現的也一樣**：決策者口頭給的新規則、主對話查出的新坑，同樣先記進表、再同步三處，不只留在對話裡。
4. **規則套用分兩種模式，公開倉庫只由主對話推送**：專案設定 `project.skill_auto_apply` 為布林，預設 `false`，缺值也視為 `false`。
   - `false`（預設，主對話套用）：排程不自己改排程規則，只在經驗表記「待套用」，狀態「待同步」；主對話核對後套進排程。
   - `true`（決策者明確選「skill 新版全部自動套用」）：只在操作排程每日結算那輪（含漏跑補做）比對到新版時，由排程的執行者（子代理或 Codex）把新版中適用本專案的規則寫進排程規則檔尾的「skill 自動套用區」，依第 5 點完成備份與核對。
   - **兩種模式共同護欄**：專案硬規則（例如開投許可範圍、每月或總預算上限、只刪暫停、不新建活動、不對外送出）不得被自動套用改動或放寬；需要改程式或腳本的條目不自動套用，記經驗表交主對話走程式審查；與專案既有規則衝突時以專案規則為準，並在經驗表記下衝突與跳過原因。「skill 自動套用區」只能新增規則或調整門檻，不能刪既有規則，也不能藉調整門檻放寬硬規則或預算上限。
   - 推上公開倉庫仍只由主對話做，排程不推；選擇自動套用不增加其他操作授權。
5. **版本跟進依設定執行**：`project.skill_version_applied` 記目前已實際套用並核對的 skill 版本（例如 `v5.21`）。操作排程每天結算那輪讀本 skill 正本 SKILL.md「目前版本」，與專案版本依各段數字比較（例如 v5.20 比 v5.9 新），不用文字排序，並讀取專案版本之後到目前版本的完整變更紀錄。
   - `skill_auto_apply=false`：有新版就在經驗表追加「skill 已到 vX，專案停在 vY，待套用：<這幾版的摘要>」，狀態「待同步」；相同版本差異已有待同步列就不重複追加。主對話把適用規則改寫進各專案排程，保留專案特有的門檻與編號；核對已套用、記明不適用項與理由後，才更新 `project.skill_version_applied`，把該列標「已同步」。
   - `skill_auto_apply=true`：排程執行者先逐條核對第 4 點護欄；改前把每份要改的規則檔備份成 `<規則檔名>.bak-<日期>-v<版本>`（日期用當日，版本用目標版號數字；已有同名備份就停下記表，不覆蓋），再把適用規則改寫進檔尾「skill 自動套用區」。改完讀回，確認新版規則已正確套用，且專案硬規則未被改動或放寬，才更新 `project.skill_version_applied`；在經驗表記一列「已自動套用 vX：套了哪幾條／跳過哪幾條與原因」。原有相同版本差異待同步列一併註明結果；需要主對話改程式或處理的跳過項另記待同步，不因版本已更新就算完成。
   - 讀不到正本、缺套用版本、版本紀錄不完整，或備份、寫入、讀回任一步失敗時，記「版本跟進未完成」與缺少項目或失敗原因，不猜、不更新套用版本、不標已同步；原有授權規則照常執行。新專案開跑就套用「目前版本」，舊專案沒有版本紀錄時先由主對話核對，不直接補成最新版。
6. **雙向迭代**：專案經驗 → 通用寫法進 skill（第 2 點）；skill 新版 → 各專案排程（第 5 點）。目標是決策規則越用越完整，新專案一開跑就拿到最新版，決策者越來越少需要討論同類問題。
7. **審查邊界**：只改規則文字、門檻與流程不用送程式審查；動到程式或腳本照原審查流程。
