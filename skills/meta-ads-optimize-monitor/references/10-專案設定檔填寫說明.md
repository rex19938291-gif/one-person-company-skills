# 10 專案設定檔填寫說明

每個專案一份設定檔（從 `templates/project-config.template.json` 複製，放在專案資料夾，例如 `config/ads-monitor.json`）。**排程 SKILL.md 只讀這份設定檔，不寫死任何帳號、編號、數字或人名**；換專案只要換設定檔。範例見 `templates/project-config.example-seminar.json`（編號已用佔位符）。

| 區塊 | 欄位 | 說明 | 找不到依據時 |
|---|---|---|---|
| project | mode | full_auto＝照規則自動加減；add_only＝只加不減；monitor_only＝只讀、記錄、建議 | 先用 monitor_only |
| project | end_date | 排程到期自動停用；長期投放填 null 並設每週檢討 | null |
| meta | result_action_type | 結果事件，**完全相等比對**，名稱含 lead 的其他項目不算 | 盤點時從實際 insights 找出 |
| meta | units | 要監控的組合（或活動）與角色：main 主組合、test 新素材測試組合 | — |
| site | signup_source | 網站實收的來源，用來交叉核對平台數字 | 沒有網站資料就不開自動加預算 |
| records | decision_queue | 待決策佇列位置，排程「需要主對話決定」一律追加 | 預設 docs/待決策佇列.md |
| goals | cost_cap_per_result | 每筆成本上限 C，多數門檻由它推算 | null＝不自動加減，只建議 |
| goals | total_budget／hard_cap | 總預算與硬上限（到了就暫停並通知） | null＝不設 |
| goals | non_session_options | 報名表裡不屬於任何一場的選項（例如「其他場次」「候補」）的值：算報名、計入成本，不算名額，回報另列「選了實際場次」的數字（references/03 二之三） | 沒有就 [] |
| goals | roi_rule | 有成交資料的專案用「營收 ≥ 廣告費才加預算」這類條件 | null |
| thresholds | raise_*／brake_*／lower_pct | 盤中加預算、盤中煞車、降幅；每次加減 ≤20% 為原則（例外：降後退回原值）。v5.6 起 `brake_spend_ratio`、`brake_cost_threshold` 停用（改用 brake_zero_spend_multiple、brake_cost_multiple），舊設定檔有這兩欄就刪掉 | 用範本預設，brake 預設關閉 |
| thresholds | brake_zero_spend_multiple／brake_evening_check／brake_cost_multiple | 盤中煞車放寬版：白天只有花費 ≥ 倍數×C 且網站 0 筆才降；有名單就到晚上那一輪看全天每筆 > 倍數×C 才降（references/03 一之二） | 2、"21:00"、1.6 |
| thresholds | cap_raise_* | 盤中碰上限加碼：開關、時段、花費比例、最少網站實收、每筆上限倍數（references/03 一之三） | 預設關；開了用 0.9、2、0.65 |
| thresholds | settle_* | 每日結算時間、漏跑補做時限、合計天數、加碼與降碼的成本倍數、兩次加碼最少間隔天數（references/03 二） | "09:00"、"12:00"、3、0.8、1.3、3 |
| thresholds | front_load | 預算前移：開關、主組合上限、保留款金額、保留起始日、名額快滿停加碼比例（references/03 二之二）；只有有結束日、總預算固定的專案用 | 預設關；金額與日期由決策者定，找不到依據就維持 null |
| thresholds | pace_relax | 進度落後放寬成本上限：`enabled` 開關、`slack_multiplier`（C_slack＝倍數×C）、`window_days`（看最近幾個完整日的實收平均）；每日需要＝還差人數 ÷ 剩餘天數（含今天），平均低於每日需要才放寬，總預算與保留款守門不變（references/03 二之四）。需要決策者先定「成本與人數哪個優先」 | 預設關；開了用 1.2、3 |
| thresholds | target_basis | 「每場目標人數」的口徑：`registrations`（報名數）或 `attendance`（出席數）。兩者需要的名單量差 2–3 倍（線上出席率常見三到五成），開工前一定先問清楚 | 不猜，先問；沒答覆前維持 registrations 並標「待確認」 |
| thresholds | insight | 主動洞察六項的門檻 | 用範本預設 |
| notify | channel | 通知方式，見 references/05「通知」 | queue_only |
| funnel | type／events | 漏斗類型（lead 名單型／purchase 購買型）與平台事件名稱（完全相等比對，只用在三來源核對小表） | 盤點時從實際 insights 找出；購買型事件名單型填 null |
| funnel | site_sources | 名單、出席、成交、營收的網站實收來源；購買型另可填網站端看商品頁 `view_content`、開始結帳 `checkout`，有填才進主表連乘 | 沒有就 null，該段不算比率 |
| funnel | windows_days／min_*／creative_gap_ratio／tracking_gap_ratio | 時間窗與樣本門檻（素材花費門檻、到站數門檻、最少轉換數）、素材報名率差距、平台與網站落差門檻 | 用範本預設 |
| funnel | benchmarks | 各段參考水準起點，見 references/11 | 用範本預設，累積 30 天後改本專案歷史值 |
| funnel | basis | 分段主表的計算基準，預設 `site`（網站基準）：平台只出花費、曝光、連結點擊，其他都用網站數字；平台事件只進三來源核對小表，見 references/11「一、計算基準」 | site |
| funnel | visitor_source | 網站端廣告訪客的來源，報名率的分母：工具（例如 ga4）、計數單位（你或工作階段）、篩選條件（utm_source／utm_medium 值或付費媒介）、拆素材用的參數（預設 utm_content）、判斷載入流失的網站端訊號 `load_signal`（例如 GA4 頁面瀏覽或自訂載入事件、速度工具）、排除平台審核機器與內部測試的條件 `exclude`（國家、螢幕解析度、停留秒數、暫停／被拒／點擊 0 的廣告也有訪客、內部 IP） | 沒有網站分析就 null，報名率只能標「Meta 口徑、可能高估」 |
| funnel | source_mismatch_ratio | Meta 連結點擊、Meta 到頁、網站廣告訪客三者差距門檻，超過就標「來源不一致」、結論降級待查 | 0.2 |
| funnel | change_log | 分界點紀錄位置（檔案路徑或試算表分頁）：頁面、表單、追蹤、素材主線每次改動的時間與內容，分段表據此切前後，見 references/11「分界點與樣本」 | docs/漏斗分界點紀錄.md |
| funnel | weekly_day／log | 每週分段週報的星期與紀錄檔 | monday、docs/漏斗分段診斷紀錄.md |

填完後在專案交接檔記下「設定檔位置、確認日期、由誰確認」，任何門檻改動都要記錄原值與新值。
